# Pixel AI Office Stage 2 — CEO и реальные AI-задачи

Это обновление накладывается поверх существующего проекта Stage 1. Оно не содержит твой `.env` и не требует менять файлы вручную по одному.

## Что добавляется

- CEO принимает цель и сразу раздаёт задания пяти специалистам (Luma 2 — исследователь, Luma 3 — продуктолог, Luma 4 — креатор, Luma 5 — менеджер продаж, Luma 6 — финансовый аналитик).
- Явные указания главнее ключевых слов: «всеми пятью специалистами», «всем сотрудникам» подключают всю команду, а «Luma 4 — слоган; Luma 6 — выручка» дают каждому названному сотруднику его собственное задание.
- Каждый специалист получает только своё задание и общий контекст, пишет только свою часть и не видит результатов коллег.
- Все задания выдаются одновременно, но модель отвечает максимум на `LLM_CONCURRENCY` запросов сразу (по умолчанию 1), остальные ждут в очереди. На CPU это значит, что пять ответов генерируются по очереди.
- В итоговом отчёте CEO есть список «Кто выполнил задачу», который строится по фактически полученным результатам, а не по тексту модели. Если сотрудник в ответе пишет от имени других, интерфейс показывает предупреждение.
- У каждого результата видны замеры: время, число токенов, скорость (ток/с), ожидание в очереди и обрезка по лимиту.
- В интерфейсе отображаются статусы, назначенные подзадачи, результаты специалистов и журнал действий.
- История задач сохраняется в localStorage браузера (до 30 задач).
- API-ключ хранится на локальном сервере в `.env`, а не в браузере.

## Установка обновления в Kali Linux

Сначала скачай `pixel-ai-office-stage2-upgrade.zip`. Перед заменой файлов создай резервную копию проекта. Если ZIP лежит в `~/Загрузки`, выполни:

```bash
cd ~/Загрузки
cp -a pixel-ai-office "pixel-ai-office-backup-$(date +%Y%m%d-%H%M%S)"
cd ~/Загрузки/pixel-ai-office
unzip -o ~/Загрузки/pixel-ai-office-stage2-upgrade.zip
```

Если браузер сохранил ZIP в `~/Downloads`, используй вместо этого путь `~/Downloads/pixel-ai-office-stage2-upgrade.zip`.

Затем установи зависимости:

```bash
cd ~/Загрузки/pixel-ai-office
npm install
```

## Подключение настоящей модели

1. Создай локальный файл настроек:

   ```bash
   cp .env.example .env
   nano .env
   ```

2. Замени `replace_with_your_api_key` на свой API-ключ провайдера модели. Сохрани файл в nano: `Ctrl+O`, Enter, затем `Ctrl+X`.
3. По умолчанию используется модель `gpt-4.1-mini`. Если она недоступна в твоём API-аккаунте, укажи в `OPENAI_MODEL` другую модель, поддерживающую Chat Completions API.
4. Сохраняй ключ только в `.env`. Не присылай его в чат, не вставляй в React-код и не выкладывай проект с ключом в публичный репозиторий.

**Важно:** API-доступ и его оплата отдельны от подписки ChatGPT. Запросы команды могут тарифицироваться провайдером. Один запуск обычно делает несколько вызовов модели: план CEO, отдельные задачи сотрудников и финальная проверка. Начинай с недорогой тестовой задачи и проверь лимиты расходов в кабинете API.

Если `.env` уже был создан, повторно копировать его не нужно. После изменения `.env` перезапусти сервер, чтобы он прочитал новые настройки.

## Как CEO понимает, кому дать задание

CEO разбирает фразу правилами, без вызова модели. Явные указания главнее ключевых слов и выбора модели.

| Формулировка | Кто работает |
|---|---|
| `Luma 4 — слоган; Luma 6 — выручка` | Luma 4 и Luma 6, у каждого своё задание |
| `Luma 2–6 …`, `с Luma 2 по Luma 6 …` | все из диапазона, общее задание |
| `всеми пятью специалистами`, `всем сотрудникам` | вся команда |
| `всем, кроме Luma 4` | все, кроме Luma 4 |
| `никого, кроме Luma 4, не подключай`, `не назначай никого, кроме Luma 4` | только Luma 4 |
| `не подключай Luma 2`, `без участия Luma 5`, `исключи Luma 3`, `Luma 6 не нужен` | все, кроме названного |
| `только Luma 4`, `исключительно Luma 4` | только Luma 4 |

Если исключены все, задача останавливается с ошибкой «Все исполнители исключены» и запрещённый сотрудник не назначается.

**Пределы разбора.** Это правила для типовых русских фраз, а не понимание языка.
- Исключение срабатывает только на конкретные слова-запреты: «не подключай/используй/привлекай/назначай…», «не надо/не нужно подключать…», «исключи(те)», «убери», «кроме», «без участия», а после имени — «не нужен», «не участвует». Между глаголом и именем допускается до четырёх слов и «пожалуйста» («Не подключай, пожалуйста, Luma 2», «Исключите из задачи Luma 2»). «Кроме» и «без» должны стоять вплотную к имени.
- Случайное «не» или «без» рядом («Не забудь подключить Luma 4», «Без задержки запусти Luma 5») сотрудника не исключает. Если такое «не» стоит в одном фрагменте с именем, CEO назначает сотрудника и пишет в плане и журнале предупреждение «Проверь: рядом с Luma N есть «не»/«без»…». В сомнительном случае правила оставляют лишнего исполнителя, а не теряют нужного, и говорят об этом.
- Общее поручение делится через «и» и запятую («Luma 2 и Luma 4 — слоган»), но не через «;» и точку: в «Luma 2; Luma 4 — слоган» Luma 2 получает ролевую часть общей цели, а не чужой слоган.
- Сложные конструкции (двойные отрицания, условия «если…, то без Luma 5», ссылки на прошлые задачи) не разбираются. Надёжнее всего формат `Luma N — задание; Luma M — задание`.
- В плане CEO (`CEO назначил: … — причина`) видно, кого назначили и кого исключили. Проверь его перед долгим запуском на CPU.

## Если `.env` был создан раньше

Обновление не меняет твой `.env`. Новые настройки работают и без него (`CEO_SUMMARY=auto`, `AGENT_SHORT_MAX_TOKENS=220`), но строка из старого шаблона их перебивает. Проверь, нет ли у тебя `CEO_SUMMARY=true`. Команда показывает только имена и значения этих настроек, ключ API она не выводит:

```bash
grep -E '^(CEO_SUMMARY|AGENT_MAX_TOKENS|AGENT_SHORT_MAX_TOKENS|LLM_CONCURRENCY)=' .env
```

Если там `CEO_SUMMARY=true`, CEO будет пересказывать результаты моделью даже для адресных заданий («Luma 4 — слоган»), а на CPU это добавляет 1–3 минуты. Замени значение на `CEO_SUMMARY=auto` или удали строку, затем перезапусти сервер. Действующие значения сервер печатает при запуске (`ceoSummary=...`) и отдаёт в `GET /api/health`.

## Задача не теряется при перезагрузке страницы

Задача выполняется на сервере, а не во вкладке:

- если обновить страницу, закрыть вкладку или пропадёт связь, сотрудники продолжают работать. Страница при открытии сама подключается к незавершённой задаче и показывает всё, что уже сделано;
- кнопка «Остановить выполнение» останавливает задачу на сервере;
- история последних 50 задач хранится в папке `data/runs/` (она в `.gitignore`) и переживает перезапуск сервера. Если сервер остановили посреди задачи, она помечается как прерванная, а уже готовые ответы сотрудников сохраняются.

**История задач.** При открытии страница подгружает с сервера задачи, которых нет в этом браузере: например, после очистки данных браузера или если офис открыт на другом компьютере. У завершённой задачи есть кнопки:
- **Повторить** — подставляет текст задачи в поле, его можно поправить и запустить снова;
- **Удалить** — убирает задачу из браузера и из `data/runs/`.

Маршруты API:
- `POST /api/runs {goal}` — запустить задачу, ответ `{runId}`;
- `GET /api/runs/:id` — задача целиком (журнал событий); `DELETE /api/runs/:id` — удалить завершённую (идущая → 409);
- `GET /api/runs/:id/events?after=N` — поток событий (SSE) с номера N; закрытие потока задачу не отменяет;
- `POST /api/runs/:id/cancel` — остановить;
- `GET /api/runs` — список задач.

Прежний `POST /api/execute` оставлен для совместимости: в нём задача по-прежнему отменяется при закрытии соединения.

## Текст появляется по мере написания

Пока сотрудник работает, в его карточке видно «Luma N пишет…» и текст, который модель генерирует прямо сейчас. Он обновляется примерно раз в 0,3 с. Когда ответ готов, черновик заменяется итоговым результатом. Модель от этого быстрее не становится, но первый текст виден через несколько секунд, а не после всего ответа. Блоки `<think>` в черновик не попадают.

## Сотрудники бегают к CEO

На сцене офиса видно, как идёт работа:
- CEO раздаёт задания: назначенные сотрудники подбегают к его столу («Понял!») и возвращаются на места;
- готовый результат сотрудник несёт CEO с листком в руке («Готово, держи!»), и на столе CEO растёт стопка сданных листов. Если модель не справилась, сотрудник тоже приходит и говорит «Не вышло…»;
- в конце команда собирается у CEO, он объявляет «Итоговый отчёт готов!», а под сценой появляется уведомление с кнопкой «Открыть отчёт». Кнопка раскрывает итоговый отчёт CEO и прокручивает к нему.

Это только анимация: работу модели пробежки не замедляют. Они показываются для событий, которые происходят сейчас. При перезагрузке страницы история задач заново не проигрывается, а во вкладке в фоне пробежки пропускаются.

## Автопроверка на GitHub

При каждом push в `main` и в каждом Pull Request GitHub Actions (`.github/workflows/ci.yml`) запускает `npm ci`, `npm run check`, `npm test` и `npm run build`. Тесты используют мок-модель и HTTP-заглушки, поэтому Ollama и API-ключ в CI не нужны. Результат виден в PR во вкладке **Checks**.

## Кто может открыть офис

По умолчанию (`npm run dev`) офис открывается **только на этом компьютере**: `http://localhost:5173/` или `http://127.0.0.1:5173/`. С телефона или другого компьютера в той же Wi-Fi-сети он недоступен.

Чтобы открыть офис для локальной сети, запусти `npm run dev:lan`. Тогда страница доступна по адресу компьютера в сети (например, `http://192.168.1.36:5173/`), и **любой в этой сети может ставить задачи**. С платным API-ключом это может стоить денег, поэтому включай этот режим только в доверенной сети.

Сервер API в любом режиме слушает только `127.0.0.1` и отклоняет:
- изменяющие запросы (запуск, остановка, удаление задач) со страниц чужих сайтов, открытых в том же браузере (`403`);
- POST не в JSON (`415`);
- запросы с чужим `Host` — защита от DNS rebinding (`421`);
- любые запросы, которые браузер пометил как пришедшие с чужого сайта (`Sec-Fetch-Site: cross-site`), в том числе GET от `<img src>` (`403`).

Проверка модели вызывает модель, поэтому она доступна только через POST: `curl -X POST http://127.0.0.1:8787/api/health/model`.

## Оценка качества ответов

`npm run eval:coffee -- --runs 3` прогоняет задание кофейни через настоящий конвейер офиса и проверяет, сделал ли каждый сотрудник **ровно то, что просили**:
- Luma 2 — 3 группы клиентов;
- Luma 3 — 3 напитка;
- Luma 4 — один слоган;
- Luma 5 — 2 способа привлечения;
- Luma 6 — выручка 90 € без выдуманных цифр.

Отдельно отмечается, если сотрудник писал за других или ответ обрезан. Результаты сохраняются в `data/evals/` для сравнения моделей и подсказок (`--model qwen3:4b`, `--label "что изменили"`).

Проверка отражает **форму** ответа (количество пунктов, один слоган, верная сумма), а не то, насколько удачны сами идеи. Замеры на qwen3:1.7b (CPU), 3 прогона:

| Что изменено | Выполнено |
|---|---|
| исходные подсказки | 9/15 (60 %): Luma 3 заполнял шаблон роли вместо напитков, Luma 6 выдумывал «затраты 60 €» |
| без описания роли для адресных заданий + «ровно N пунктов» | 13/15 |
| + калькулятор офиса | 13/15: Luma 6 3/3, Luma 3 неустойчив |
| + «пункт начинается с названия, допущения после списка» | **15/15** |

**Калькулятор офиса.** Маленькая модель плохо считает, поэтому сервер сам точно вычисляет арифметику из задания («30 × 3») и подсказывает сотруднику ответ: «30 × 3 = 90». Диапазоны («2-3 варианта», «100 - 15») калькулятор не трогает.

## Честные ограничения

Это настоящие последовательные вызовы языковой модели, а не таймерная симуляция. Однако сама по себе модель не гарантирует правильность ответов и **не выполняет внешний веб-поиск, рассылку, публикацию, покупки или получение оплаты**. Она может подготовить планы, черновики, анализ и другие материалы. Проверяй источники и результаты перед действиями с клиентами. Все внешние действия должны быть отдельной интеграцией и требовать твоего одобрения.
